日期：2026-09-22。已同步本地代码与生产服务器。

## 现场证据与结论

真实订单 LIMS-2026-0164 当前排期为9月23～24日，样品已入库。负责人端分别从“我的排期”和“订单详情”打开重新排期，均能正常显示弹窗；原日期与提前日期的设备查询都返回200。未复现“仅点击打开就报错”，用户的原始报错文本尚未获得，不能断言所有描述中的异常均已定位。

已确认可导致改期失败的交互缺陷：日期变化调用 resetDeviceSelection，直接清空原设备。手动查询返回原设备可用时，代码仅检查已选设备是否失效，不会恢复已被清空的选择，因此只修改日期就提交会触发“未选设备”校验。这个问题同时存在于 LabView 和 ScheduleView，影响负责人和操作员。

## 五个方面的处理

| 方面 | 排查结论及处理 |
| --- | --- |
| 流程设计 | 已排期、未结束任务允许提前；更改日期或设备后须销售重新确认。保留现有规则，不绕过待处理变更、已结束或跨实验室权限限制。 |
| 前端 | 日期修改后自动查询新日期可用设备；原设备可用时保留，不再要求无意义地重新选同一台设备。冲突时清空并显示原因，引导选择其他设备。 |
| 后端 | 现有接口允许今天日期，设备冲突计算排除了当前任务本身；负责人和本实验室操作员均有权限。专项测试覆盖自占用排除、真实冲突和跨实验室拒绝，无需放宽校验。 |
| 数据库 | 日期字段可正常存储今天日期，无需迁移或修复真实订单数据；失败改期保持原日期及销售确认，成功记录操作人及流程事件。 |
| 前后端交互 | 提交前再次复核当前日期，避免刚编辑日期或设备占用变化时使用过期结果；查询期间禁用设备选择及提交，丢弃旧请求响应；查询失败后重试仍保留原设备候选。 |
