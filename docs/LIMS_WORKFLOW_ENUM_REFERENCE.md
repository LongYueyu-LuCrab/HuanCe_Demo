# HuanCe LIMS 当前流程与枚举对照

> 这份文档以当前代码为准，尤其区分“订单状态”和“报告状态”。
> 两者都叫 `status`，但数值空间完全不同，前端字段也不同：
> - 订单：`status_key` → `LabOrder.Status`
> - 报告：`latest_report_status_key` / `report.status_key` → `TestReport.Status`

## 一、先记住最容易混淆的结论

| 业务文字 | 所属对象 | 枚举 | 数值 |
|---|---|---|---:|
| 报告审核中 | 订单 `LabOrder` | `REPORT_REVIEW` | **5** |
| 待销售初审 | 报告 `TestReport` | `SALES_REVIEW` | **2** |
| 待总经理终审 | 报告 `TestReport` | `GM_REVIEW` | **3** |
| 实验结果已提交待出报告 | 订单 `LabOrder` | `TEST_FINISHED` | **8** |
| 实验已结束待提交结果 | 订单 `LabOrder` | `RESULT_PENDING` | **9** |

因此，订单 `LIMS-2026-0185` 的正确组合是：

```text
order.status_key = 5
order.status = 报告审核中 / 页面可能按最新报告显示为待销售初审
order.latest_report_status_key = 2
order.latest_report_status = 待销售初审
```

前端判断销售审核入口必须同时使用：

```text
order.status_key == 5
and order.latest_report_status_key == 2
and 当前角色具备销售审核权限
```

## 三、订单主状态 `LabOrder.Status`

| 数值 | 枚举 | 页面文字 | 进入/离开说明 |
|---:|---|---|---|
| 1 | `PENDING_REVIEW` | 待评审 | 销售创建或驳回后修改重提；等待商务/技术双评审 |
| 2 | `REVIEW_REJECTED` | 评审驳回 | 商务或技术评审驳回；销售可修改重提或退单 |
| 3 | `SCHEDULING` | 排期中 | 双评审通过后进入；V1 由质量部排期，V2 由实验室/商务协同排期 |
| 4 | `TESTING` | 试验中 | 至少有路径进入试验执行 |
| 5 | `REPORT_REVIEW` | 报告审核中 | 报告已出具并进入销售/总经理审核；订单层面贯穿报告审核到最终开票前 |
| 6 | `INVOICED_CLOSED` | 已开票办结 | 会计完成最终总开票，流程结束 |
| 7 | `CANCELLED` | 退单 | 销售退单，流程终止 |
| 8 | `TEST_FINISHED` | 实验结果已提交待出报告 | 所有执行路径实验结果已正式提交，等待出具报告 |
| 9 | `RESULT_PENDING` | 实验已结束待提交结果 | 所有路径已结束，但至少一条实验结果尚未正式提交 |

### 订单主状态的典型流转

```text
1 待评审
 ├─ 双评审通过 → 3 排期中
 ├─ 任一评审驳回 → 2 评审驳回 → 销售修改重提 → 1
 └─ 销售退单 → 7 退单

3 排期中 → 4 试验中
4 试验中
 ├─ 所有实验结束但仍有结果未提交 → 9 实验已结束待提交结果
 ├─ 所有路径结果正式提交 → 8 实验结果已提交待出报告
 └─ 试验中变更 → 3 排期中，等待重新排期

8 → 主责角色出具报告 → 5 报告审核中
9 → 补齐实验结果 → 8
5 → 销售初审 → 报告状态 3
5 → 销售驳回 → 报告状态 4，回质量/主责实验室重制
5 → 总经理终审通过 → 报告状态 5 → 会计最终开票 → 6
```

注意：订单从 `5` 到最终开票前仍保持 `REPORT_REVIEW = 5`，报告审核阶段要看报告子状态，不要把订单状态数值和报告状态数值替换使用。

## 四、排期任务状态 `SchedulePlan.Status`

| 数值 | 枚举 | 页面文字 | 典型动作 |
|---:|---|---|---|
| 1 | `NEW` | 新建 | 任务已创建，等待排期/排台和样品处理 |
| 2 | `CHANGE_PENDING` | 变更待调整 | 订单变更后锁住开始试验、提交结果和出报告，先处理变更并重新排期 |
| 3 | `RUNNING` | 执行中 | 已排期并开始执行；可继续实验、结束实验或发起试验中变更 |
| 4 | `ENDED` | 实验已结束待提交结果 | 实验结果已录入但尚未点击正式提交结果 |
| 5 | `FINISHED` | 结果已提交 | 当前执行路径结果已正式提交 |

后端计算的路径执行状态还包括：

| `execution_state` | 含义 |
|---|---|
| `schedule` | 未排期或变更待调整 |
| `sample` | 已排期但样品未到 |
| `ready` | 已排期、样品已到，可以开始试验 |
| `running` | 实验进行中 |
| `result_pending` | 实验已结束，等待正式提交结果 |
| `completed` | 当前路径结果已提交 |
| `outsource` | 委外路径待回传/执行中 |

## 七、实验记录状态与结果枚举

### `Experiment.Status`

| 数值 | 枚举 | 页面文字 | 操作 |
|---:|---|---|---|
| 1 | `WAITING` | 待开展 | 尚未开始 |
| 2 | `RUNNING` | 试验中 | 可执行“实验结束” |
| 3 | `ENDED` | 实验已结束待提交结果 | 可执行“提交结果” |
| 4 | `FINISHED` | 结果已提交 | 当前实验记录完成 |

### `Experiment.Result`

| 值 | 页面文字 |
|---|---|
| `pass` | 合格 |
| `fail` | 不合格 |
| `abnormal` | 异常 |
| `retest` | 待复测 |

实验流程刻意拆成两步：

```text
实验中 → 实验结束（保存数据和结论，Experiment=ENDED）
      → 提交结果（正式提交，Experiment=FINISHED）
```

只点“实验结束”不会进入待出报告；必须继续点击“提交结果”。

## 十、主要角色与动作

|---|---|
| 销售 | 创建订单；处理自己订单的评审驳回；销售初审报告；可发起自己订单变更 |
| 商务部 | 销售协同、订单评审/路径协同、自己归属订单相关动作；报告初审需受销售归属校验 |

## 十二、前端显示判断规范

1. 订单列表中的状态按钮先看 `order.status_key`，再看角色和路径；不要用报告状态数值替代订单状态。
2. 报告审核按钮看 `latest_report_status_key` 或报告列表的 `report.status_key`。
3. `订单 5 + 报告 2` 才是“待销售初审”；`订单 5 + 报告 3` 才是“待总经理终审”。
4. 订单 8 是“实验结果已提交待出报告”，订单 9 是“实验已结束待提交结果”，不能互换。
5. “实验结束”和“提交结果”是两个独立动作；委外回传后也要继续提交结果。
6. 待处理更改单存在时，后端会阻断排期、开始实验、提交结果和出报告动作；前端也应隐藏或提示这些动作。
7. 任何前端按钮都不能代替后端权限和状态校验；新增动作必须同时检查四层：后端接口、后端权限/状态、序列化字段、前端按钮条件。

## 十三、这次 BUG 的复盘

这次错误来自新增销售初审入口时只记住了页面文字，没有先查对象和枚举归属：把 `TestReport.SALES_REVIEW = 2` 正确记住了，却把订单层的 `LabOrder.REPORT_REVIEW = 5` 错写成了 8。今后凡是新增流程按钮，先按以下顺序核对：

```text
1. 入口对象：订单 / 排期 / 样品 / 实验 / 报告 / 发票
2. 对应模型：LabOrder / SchedulePlan / Sample / Experiment / TestReport / Invoice
3. 对应枚举类和值
4. 后端接口的状态校验
5. 后端 payload 字段
6. 前端按钮条件
7. 真实角色和真实订单验证
```
